# 港口建设与客货航线验收指南

本指南用于通过 CityWeaverMCP 建设大型模块化港口、添加集装箱吊臂和客运楼、连接航道并开通客货航线。这里的“大型港口”是由港口大门、单向港口道路和多个泊位模块组成的完整港区，不是只放置一个货运码头。默认不放置侧门；只有用户明确要求时才纳入侧门方案。普通独立港口沿用主体选址、航道连接和运营验收流程，但不应套用模块化港区的内部环路规则。

依据：2026-09-27，游戏 1.6.2f1，曼宁顿存档的实机建设与修复。当前工具参数、资产名称和限制以运行中的 MCP schema 与 `get_query_capabilities` 为准。文中的数值用于解释这次案例，不能直接复制为其他城市的施工参数。

## 1. 建设顺序与完成标准

模块化港口施工顺序：现场勘察 → 港口大门与陆侧接入（默认无侧门） → 单向港口道路闭合环路及陆侧作业区 → 先放置集装箱吊臂/客运楼 → 回读建筑自带航道的永久端点 → 连接泊位接驳航道与主航道 → 开通客货航线 → 实际运行验收。普通独立港口按其 prefab 建设主体和陆侧接入，跳过不适用的内部环路、作业区配额及模块升级步骤。

**吊臂和客运楼均须先建建筑，再接航道，最后开通航线。** 不在计划泊位范围内预先铺设接驳航道，以免与建筑自带航道重叠或改变其接头。规划器因缺少附近永久、无建筑 owner 的航道而过滤候选，是候选生成限制，不能视为原生施工的必需前置条件，也不能因此倒置施工顺序；处理方式见第 4.1 节。已有主航道保持保留，合法吸附与包络重叠以原生校验为准。模块建成后必须重新读取节点和通道；原生合并会改变接头形状，先前通过的航道不保证最终泊位可用。

| 阶段 | 必须取得的证据 |
| --- | --- |
| 港区道路建成 | 模块化港口内部使用单向道路，形成入口—作业区—出口闭合环路；默认仅经主大门对外连接，不放置侧门；普通独立港口按自身入口验证道路可达，不要求此环路 |
| 主体、升级建成 | 操作 `completed`；永久实体存在；Owner、道路绑定、升级数量正确 |
| 岸线泊位有效 | 岸上基础和岸侧标记满足干地及附着规则；船舶航道满足全宽水深要求；集成停靠点按自身放置规则检查，无原生表面或碰撞错误，合法航道吸附不作为冲突 |
| 航道接通 | 永久边和节点形成到主航道的连续拓扑；泊位实际子通道仍覆盖停靠点 |
| 航线创建 | 操作 `completed`；站序、客货类型、启用状态正确 |
| 航线可寻路 | 航点 `RouteLane` 两端非空；两个方向有有效 `PathElement` 和正的路径距离 |
| 航线运行 | 实际船舶沿有效路径驶向码头并离港；进一步观察上下客或装卸 |

**建筑建成、线路 `complete=true`、首船生成，都不能单独证明港口可以运营。**

## 2. 施工前发现与勘察

1. 调用 `get_game_status`、`get_query_capabilities`，确认城市已加载，记录会话 ID 和原模拟速度。
2. 查询 `list_transport_facility_prefabs`、`list_transport_facilities`；扩建已有港口时读取 `list_transport_facility_upgrades`。
3. 查询 `list_waterway_prefabs`、`list_waterways`、`get_waterway`，发现可用航道和外部连接方向。
4. 用 `sample_terrain`、`read_surface_water_mask` 检查岸上平台、陡岸、泊位及全宽航道水域；检查道路、已有设施和路口净空。
5. 用 `list_transport_stops(transport_type="Ship")` 和 `list_transport_lines` 了解现有客货服务，避免重复建线。

大型模块化港口的勘察还要按实时 prefab 目录统计计划内的货仓、储罐区、货物堆场和集装箱堆场尺寸、升级范围、道路连接侧及重复安装限制。其港区边界不能只包住大门、环路和岸边模块；必须预留至少两种上述陆侧作业设施的完整物理占地，优先让四种都能落位。普通独立港口按自身功能和本次建设范围规划配套，不套用这一设施配额。预算要包含主体、升级、接驳航道、陆侧作业设施和可能的返工。暂停城市后施工；所有预览与提交遵循对应工具的事务流程，完成验收后恢复原速度。实体 ID 只在当前城市会话有效，重载后重新发现。

## 3. 港口主体、内部环路与陆侧接入

新建主体先从实时 prefab 目录确认是否为独立港口或模块化主门。依据返回的放置模式生成候选，经 `preview_transport_facility_placement` 原生预览、费用核对、提交和永久回读后，再规划升级。建筑选址和提交细节见[建筑指南](../buildings/BUILDING-GUIDE.md)及[交通设施指南](TRANSPORT-INFRASTRUCTURE-GUIDE.md)。

### 3.1 大型港口的四道结构门禁

以下规则适用于本指南的大型模块化港区规划，普通独立港口不适用内部环路、专用门和作业区配额要求。模块化港区进入泊位模块施工前须通过这些门禁，不能以“画面上看起来连通”代替永久拓扑回读。

1. **内部道路必须使用单向道路并形成入口—出口环路。** 从实时资产目录确认港口道路、港口大门道路及兼容埠头道路的单向属性，不能仅凭名称判断；主环路和作业区支路均使用单向道路。道路必须从港口入口进入、经过计划中的泊位和作业区，再连到出口，形成可连续行驶的闭合环路；支路须顺向汇回环路。死胡同、反向边、两段彼此靠近但没有共同节点、只连接入口没有出口，都不合格。单向资产无法通过岸线预览时，应检查地形或重新选线，不能自行改用双向道路。
2. **默认不放置侧门，对外连接仅经过主大门。** 主大门可分别提供入口和出口；只有用户明确要求侧门时，才按资产规则规划侧门。普通道路不得从围界中段、泊位背面或内部环路任意节点穿出。先在规划图中列出全部边界穿越点，再用永久道路端点和连接边回读；发现未经规划的外接口时停止后续施工并修正。
3. **泊位道路必须是真正的水陆边界。** 承载集装箱吊臂或客运楼的港口道路/埠头，一侧为可承载岸上基础的连续陆地，另一侧为可通航水域。按子对象分别检查：岸侧 `Ship Stop Location` 须满足不被淹没及道路附着规则；集成客货停靠点按自身原生放置标志检查表面与通道连接，不能因名称含 Ship 就要求其标记坐标有水；模块自带航道和计划接驳则检查全宽水深。覆盖完整 prefab 及子对象范围，不只采样建筑中心。水深预筛阈值须结合实时工具、资产和原生预览验证，没有适用于所有子对象的统一最低水深。
4. **港区面积必须容纳后方作业区。** 在闭合环路内或与环路直接服务的港区用地中，为货仓、储罐区、货物堆场、集装箱堆场分别尝试预留位置。最少必须能按原生规则放置其中两种，规划目标是四种全部可放置。预留按当前城市实时 prefab 的完整物理尺寸、旋转后包络、道路接入侧和升级占地计算，不能用概念图标或建筑主体模型估算。环路、泊位、路口、铁路/管线、排队车道、装卸通道和设施之间的原生净空不得计入可用堆场面积。

门禁验收至少记录：港区道路 prefab 及单向属性、主大门入口和出口节点、内部道路有向连通关系、所有外部连接节点、岸线道路两侧的地形与水深采样、泊位模块包络，以及四类陆侧设施的 prefab、尺寸、候选位置和预留状态。须证明入口能到达全部作业段，且各作业段均能顺向到达出口；若用户明确要求侧门，另记录其节点及要求来源。大型港口不满足任一道门禁时，不安装吊臂、客运楼，也不开通航线。

### 3.2 港区规模与作业区布局

本节仅适用于大型模块化港区；普通独立港口不要求预留两类或四类升级设施。

先用全部四类设施做“最大方案”，再在地形、资产解锁或预算确实不允许时降级；不能一开始就只按最低两类缩小港区。

| 作业设施 | 规划目的 | 位置与连接重点 |
| --- | --- | --- |
| 货仓 | 普通货物暂存、分拨和与陆侧物流衔接 | 靠近环路和主要货车流线，避免占用泊位正后方装卸净空 |
| 储罐区 | 液体或散装货物储存 | 与客运楼、主要步行区和拥堵路口保持安全间隔；按实时 prefab 的道路及专用连接要求布置 |
| 货物堆场 | 散杂货、重件或开放式堆存 | 需要连续大块平整用地和重型车辆转弯空间，不用零碎边角拼接名义面积 |
| 集装箱堆场 | 集装箱周转及吊臂后方缓冲 | 优先与集装箱吊臂形成短而直接的货物流线，同时保留环路通行和排队空间 |

规划图应为每类设施建立独立的预留包络和道路绑定意图，并标注 `required` 或 `preferred`：至少两类标为必须建成，剩余类型保持优先预留。若四类均有合法候选，则不得为了缩短道路或减少一次施工而取消其中任何一类。多个设施可以共享港区环路，但不能共享同一物理占地，也不能阻断入口—出口闭合路径。

面积验收不能只比较港区总面积。应逐一验证每个预留包络位于已购、可建设且坡度/地形合格的陆地，存在兼容道路接入，并与泊位隐藏子对象、其他设施、道路和计划网络保持净空。最终仍以各设施的原生预览为准；“图上放得下”只证明概念容量，不证明可施工。

### 3.3 主体与陆侧交通

需要同时考虑；其中大门、专用内部道路、闭合环路及作业区配额只适用于大型模块化港区，普通独立港口仍须验证自身道路、步行和公用设施接入：

- 主体入口连接可寻路道路；货车有进入城市货运路网的通道。
- 城市普通道路默认止于主大门；大门内侧再转换为单向港口道路，不放置侧门。只有用户明确要求时才增加侧门接入。不要用普通城市道路替代港区环路，也不要让港口道路绕过大门直接接出。
- 入口与出口方向、单向限制和转弯关系允许货车完整绕行港区。拓扑闭合但方向上无法从入口到出口，仍视为失败。
- 客运楼有陆侧道路与步行接驳，建筑和附属碰撞体不压住道路或路口。
- 供电、给水、污水等服务实际连接；暂停时需求读数为零不代表供能合格。
- 主体升级范围能够覆盖计划中的泊位；使用游戏计算的范围和候选，不凭主楼到码头的直线距离估计。
- 环路服务泊位的同时，应至少经过两类已选作业区，并尽量覆盖四类；货车不应为了到达货仓或堆场而穿过客运楼主要步行区。

本次扩建使用现有 `CargoHarborComplex03` 主体，没有重新建设主楼；这次实测不覆盖所有港口主体的从零放置。新港照此规划时，先完成上述结构门禁，不能仅复制本次泊位模块的坐标或道路长度。

## 4. 添加集装箱吊臂与客运楼

本次使用的升级为 `CargoHarborComplexCrane02`（120,000）和 `HarborComplexPassengerTerminal01`（200,000）。这些名称和费用只描述本次资产，施工时必须重新查询。

1. 从 `list_transport_facility_upgrades` 确认兼容、解锁和已安装数量。
2. 读取 `placement_geometry.road_side_candidates`，选择实际目标港口岸线上的候选。范围可能覆盖邻港，排名靠前不代表属于预期位置。候选还必须落在已经通过第 3.1 节门禁的港口道路或埠头上，普通城市道路即使进入范围也不能作为替代。
3. 将候选的 `position`、`rotation_degrees`、`road_edge_id` 原样传给 `preview_transport_facility_upgrade`，使用 `placement_mode="road_side"`。
4. 轮询 `get_building_operation`。只有 `preview_ready`、可提交且错误已排除，才调用 `apply_building_operation`，设置足够的 `max_cost`。
5. 等待 `completed`；回读升级列表、永久实体 `Game.Common.Owner` 和 `Game.Buildings.Building.m_RoadEdge`。
6. 重新发现升级的 `SubNet`、`SubObject` 和实际 Ship 停靠点，为后续接驳与航线提供真实对象。

不要直接修改候选坐标绕过失败。本次 Crane02 具有 `CanBeOnRoad`、没有 `CanBeOnRoadArea`；原生 `ObjectToolSystem` 将它吸附到道路中心线。把吊臂横移 5m 并不符合该资产的原生吸附规则，不能据此放宽 MCP 校验。

### 4.1 模块与航道的施工顺序

吊臂和客运楼会生成隐藏停靠点、自有 `Pier Seaway`、附着标记及较大的原生碰撞包络。两类建筑均按“先建筑、后航道、再航线”的顺序施工，避免预建接驳与建筑自带航道重叠：

1. 保留现有主航道和外部连接，预留全部计划泊位的建筑及子对象包络；不在该范围内先铺接驳航道。
2. 在已通过门禁的永久单向岸线道路上取得合法候选，逐一预览并安装本次计划的吊臂和客运楼。保留模块之间的原生净空；只有原生预览通过才提交。
3. 全部计划泊位模块建成后，回读永久实体的 owner、道路绑定、`SubNet`、停靠点和自带航道的真实端点。不得拿预览坐标或建筑中心代替端点。
4. 从这些真实端点规划接驳航道并连接主航道，检查全宽水深与接头切线，经原生预览后提交。已有连接有效时无需重复补建。
5. 回读永久航道拓扑及各泊位实际子通道，确认接头没有压缩或移走停靠通道；通过后再创建客货航线，执行寻路和运行验收。

若规划器仅因缺少既有航道吸附目标而不返回候选，应核查候选过滤逻辑，使用支持先放建筑的合法道路绑定规划能力；当前工具无法提供时，应报告或修复该规划器限制。不能为了填充候选列表而先建接驳航道，也不能手改候选坐标或绕过原生校验。

如果模块预览列出 `Pier Seaway`、`Narrow Seaway` 或其他航道对象的 `OverlapExisting`，不要继续在同一点重复提交，也不要删除模块拥有的内部边。先确认碰撞对象、owner、是否为本次新增及线路依赖；合法吸附不作为碰撞处理。在已有授权覆盖拆除且准备好恢复路径时，才调整或移除造成冲突的接驳边；存在运行线路依赖时先安排迁移或中断恢复。随后重新取得合法建筑候选，先完成模块，再按真实端点恢复连接。若主航道与泊位持续发生原生碰撞，应重新规划岸线或港池，不应靠反复拆建碰运气。

### 4.2 读取真正的失败原因

建筑操作的 `errors` 可能只是 prefab 名称。应读取 `validation_details` 中的：

- `native_error_codes` 与 `native_error_decoded`；未解码不等于无错误。
- 报错对象位置、owner、附着父对象和 `attached_parent_original_id`。
- `commit_dispatched`、永久结果列表，确认预览是否真的改变了城市。

`Ship Stop Location`、`Integrated Cargo Ship Stop`、`Integrated Passenger Ship Stop` 是不同子对象。本次吊臂岸侧标记距中心约 10m、水侧停靠点约 18m；客运停靠点约 14m。只看建筑中心的水深会漏掉真正的错误位置。

### 4.3 陡岸的 InWater 不一定是积水坑

本次岸侧标记报 `InWater`，却已正确附着到码头道路。核对水网格和地形后发现：岸外格点有水、岸内格点无水；游戏对水深做双线性插值，再加上另行采样的陡岸地形高度，得到偏高的校验水面。水网格间距在该地图为 7m。

处理步骤：

1. 在报错子对象坐标采样，而非仅在建筑中心采样。
2. 对岸线做地形/水深剖面，区分真实封闭积水、正常海水和陡岸插值影响。
3. 如短暂运行水模拟后无变化，不应无限等待或直接开沟。
4. 优先寻找其他合法候选；确需拓宽岸边平台时，先确定范围、目标高度、次数和影响，再在授权范围内执行。
5. 地形操作完成后回读高度和水深，重新做建筑预览；新报错可能来自另一个子对象。

本次局部整平使用长 36m 的路径、24m 刷宽、目标高度约 516.445m，先 1 次、另经确认后追加 8 次。路径中心原地形约 502m，实际涉及约 14m 填高，不能称为微小高度修正。边缘衰减使单次整平未能消除水侧停靠点的插值影响；追加后通过。

这些数值**不是通用修复配方**。`preview_terrain` 只是参数与基线预检，不显示临时变形，也不保证最终高度；地形没有精确撤销。不要用全图 `flatten_map/clear_water` 解决局部泊位问题。参见[地形指南](../areas/TERRAIN-GUIDE.md)。

## 5. 航道接驳：节点接通后还要检查泊位通道

1. 用 `get_waterway` 读取内部 Pier Seaway、owner 和端点 ID。
2. 再读取端点的 `Game.Net.Node.m_Position`、`ConnectedEdge`。建筑吸附合并后，实时节点位置可能不同于边的原始 Bezier 端点；以实时节点与当前拓扑设计连接。
3. 用实际节点 ID 连接，检查全宽水深和接头切线，运行 `preview_waterway` → `get_waterway_operation` → `apply_waterway_operation`。
4. 等待 `completed`，回读新边、节点连通和相邻建筑内部航道。
5. 读取泊位边的 `Game.Net.SubLane`，再读取船舶通道的 `Curve`、`CarLane` 和 prefab 类型；检查通道位置与长度是否仍能服务停靠点。

游戏船舶通道也可能使用 `CarLane` 和 `PathMethods.Road`，不能仅凭字段名称误判成汽车道路。

### 5.1 本次客运失败的关键教训

一段 Narrow Seaway 在客运楼建成前通过预览；客运楼接入后，其接头把 72m 的内部 Pier Seaway 的实际船舶子通道压缩到约 **0.34m**，通道集中在泊位一端，远离停靠点。建筑和航道都能显示“完成”，但客运航点 `RouteLane` 两端为空，双向线路段没有路径。

修复时删除的是本次新增、无建筑 owner 的接驳边，保留客运楼、吊臂和主航道。待客运码头端点恢复后，使用两端真实节点连接同型 `Pier Seaway`，原生预览通过，停靠点自动恢复通道绑定。

结论是**按真实端点重做接头并回读子通道**，不是“所有接驳都必须换成 Pier Seaway”。类型、宽度和几何需要共同验证。不要单独拆除建筑拥有的内部航道；拆除已有接驳前先检查依赖、准备恢复方案，并确认授权。详见[航道指南](WATERWAY-GUIDE.md)。

## 6. 创建客运与货运航线

只有本次计划的吊臂和客运楼已建成、后续接驳航道及泊位子通道已验收，才进入航线创建。先调用 `list_transport_line_prefabs` 和 `list_transport_stops(transport_type="Ship")`：

| 用途 | 本次线路 prefab | 站点要求 |
| --- | --- | --- |
| 客运 | `Passenger Ship Line` | 新客运楼的 passenger 停靠点 + 兼容外部连接 |
| 货运 | `Cargo Ship Route` | 新吊臂的 cargo 停靠点 + 兼容外部连接 |

确认停靠点 Owner 属于目标模块；不要把主楼 ID、模块 ID 或航道节点 ID 当作 `stop_id`。目的地依据现有航道、外部连接和服务需要选择，本次选择较近的东部外海，保留右港已有航线。

1. `preview_transport_line`：传精确 `line_prefab`、线路名称和有序 `stop_ids`；两站往返传两个站，工具创建闭合线路。
2. 轮询 `get_transport_line_operation` 到 `preview_ready`，检查错误和警告。
3. `apply_transport_line_operation` **沿用该预览的同一 `request_id`**。
4. 等待 `completed`，使用 `result_line_id` 回读永久线路。
5. 检查 `active`、`schedule`、站序、实际票价和船舶数。新线路某些字段需运行模拟后才更新。

不要在未知结果时换 request_id 重建线路。详见[线路指南](TRANSPORT-GUIDE.md)。

## 7. 必须执行的航线验收

### 路径验收

- 读取线路 `RouteWaypoint`，检查各航点 `Connected` 指向预期站点。
- 检查各航点 `Game.Routes.RouteLane.m_StartLane/m_EndLane` 非空。
- 读取线路 `Game.Routes.RouteSegment`，逐段检查 `Game.Pathfind.PathElement` 非空、`PathInformation` 距离有效。
- 对两站往返线路，两个方向都要验证；不能只检查其中一段。
- `route_distance_m=-2` 不是有效长度。本次它对应两个 -1 的空路径，必须继续检查，不能当作单纯显示延迟。

2026-09-27 的运行版本中，MCP 线路工具的预览状态依赖临时线路对象和原生错误标签，未额外要求所有航点 lane 与分段路径有效。因此 `preview_ready` 和 `complete=true` 不能替代上述检查。

### 运行验收

在没有未完成写事务时短暂推进模拟，随后暂停回读：

1. `get_transport_line` 确认实际船舶，不仅是待处理车辆请求。
2. `get_vehicle` / `get_vehicle_path` 确认有效目的地、非空路径、移动及未卡住。
3. 至少观察船舶驶向本地泊位，然后检查泊位 `BoardingVehicle` 或返程路径起点，确认服务目标没有错配。
4. 长期运营另查实际上下客、装卸、班次与陆侧接驳。空船或零候客不等于航道失败，也不等于需求已经满足。

本次修复后的客运双向路径各有 20 个元素，距离约 4440.01m 和 4272.54m，往返约 8712.55m；实船先驶向左港，随后读取到从左港航点返回外海的有效路径。货运往返约 8384.49m。没有直接截取到客船 BoardingVehicle 占用瞬间，也没有验证持续载客或装卸吞吐。

## 8. 施工放行检查清单

先记录港口类型和本次施工范围，再按 A → B → C 核查适用项。普通独立港口将 A 组标为“不适用：独立港口”，直接执行 B 组的主体/岸线检查和 C 组的航道/线路检查；没有升级模块的项目不检查模块 owner 或升级数量。适用的前置项未通过时，不进入依赖它的后续施工。“不适用”须写明原因，不能用于跳过尚未验证的要求。

### A. 港区结构（仅大型模块化港口）

- [ ] 已确认目标是大型模块化港口，而非单一货运码头。
- [ ] 内部主环路和作业区支路均使用已确认单向属性的港口道路资产，构成永久闭合环路。
- [ ] 从入口沿允许行驶方向可到达全部作业段并从出口离开。
- [ ] 默认不放置侧门，仅经主大门对外连接；若有侧门，已记录用户明确要求。不存在未经规划的外接口。
- [ ] 普通城市道路没有穿入港区并替代内部港口道路。
- [ ] 已按实时 prefab 完整尺寸分别尝试预留货仓、储罐区、货物堆场和集装箱堆场。
- [ ] 至少两类作业设施具有互不重叠、可接入环路且能进入原生预览的独立位置；其余两类已尽量保留候选和扩建空间。
- [ ] 最大方案能够容纳四类时，规划没有无故降级为两类。

### B. 主体、岸线与模块（按资产类型核查）

- [ ] 主体按自身 prefab 满足道路和岸线放置要求；如安装吊臂/客运楼，其候选绑定目标港口的永久岸线道路或埠头，不属于邻港或普通城市道路。
- [ ] 岸上基础有连续稳定陆地；岸侧标记按自身规则检查不被淹没及正确附着，未将其误列为必须有水的区域。
- [ ] 集成客货停靠点按自身原生规则检查表面和连接；自带航道及接驳按全宽检查水深，检查覆盖完整建筑及子对象范围。
- [ ] 吊臂和客运楼均先放置建筑，未为生成候选而预建接驳航道；合法吸附重叠未被当作碰撞排除，真正的原生错误已解决。
- [ ] 如需拆改碰撞边，已检查 owner、线路依赖、授权及恢复方案，并在拆改后重新取得合法建筑候选。
- [ ] 主体或模块原生预览为 `preview_ready`、`can_commit=true`、无错误；提交后永久实体及所需道路绑定正确，模块另核验 owner 和升级数量。

### C. 航道与线路

- [ ] 本次计划的吊臂和客运楼已先建成，再使用回读的自带航道真实端点建设接驳，没有用建筑中心或概念坐标代替节点。
- [ ] 接驳航道与主航道/外部连接形成连续永久拓扑，设施自有船舶子通道仍覆盖停靠点。
- [ ] 航道验收后才开通客货航线；停靠点属于正确主体/模块，航线使用正确类型的 `stop_id`。
- [ ] 双向 `RouteLane`、`PathElement` 和路径距离有效，并观察到实际船舶按预期进出港。

检查结果应附带实体 ID、operation ID、坐标/节点、错误详情和回读时间。适用项未知时写为“未验证”，不能写成“通过”或“不适用”。

## 9. 常见问题速查

| 现象 | 优先检查 | 处理方向 |
| --- | --- | --- |
| 港区道路看似成环但车辆不能绕行 | 永久节点、边方向、单向限制、入口到出口路径 | 修复断点或方向；不能用画面相交代替共同节点 |
| 港区出现多个外部路口 | 所有边界穿越点、道路 owner/prefab、连接节点及用户是否明确要求侧门 | 默认仅保留主大门接入，不放置侧门；在授权范围内修正其他连接后重新验收 |
| 港区只能放大门和泊位 | 四类作业设施的实时尺寸、旋转包络、升级范围和道路净空 | 扩大港区或重排环路；至少保证两类，优先为四类全部保留位置 |
| 总面积足够但货仓/堆场无合法候选 | 可用连续地块、道路接入侧、坡度、路口与隐藏子对象碰撞 | 不按总面积判断；重新划分连续作业地块并逐设施原生预览 |
| 吊臂候选落在普通道路或邻港 | `road_edge_id`、道路 prefab、主体 owner 与升级范围 | 重新发现目标港口候选；不手改坐标或借用邻港候选 |
| 候选道路两侧都是陆地或都是水 | 道路法线两侧的地形、水面和完整模块包络 | 重选真正水陆边界的港口道路/埠头；必要时重新规划港池 |
| 吊臂或客运楼与航道碰撞 | 原生错误码、碰撞边 owner、线路依赖及是否先铺了接驳 | 区分合法吸附与真正碰撞；调整合法候选或获授权的接驳边，先安装建筑，再按自带航道真实端点连接 |
| 没有道路侧升级候选 | 主体范围、兼容单向码头道路、候选截断及既有航道过滤条件 | 核查或修复候选生成限制；不为生成候选先铺接驳，不手改候选坐标，不绕过原生校验 |
| `Ship Stop Location: InWater` | 子对象位置、真实附着父道路、岸边水深剖面 | 换候选或制定局部地形方案；先区分积水与插值 |
| `OverlapExisting` | `validation_details` 中碰撞对象及 owner | 调整到其他返回候选；检查建筑隐藏碰撞体和路口 |
| `InvalidShape` | 接头角度、宽度过渡、短边、合并后的节点位置 | 重做接驳走向；每次检查相邻泊位实际子通道 |
| 线路完成但距离为负 | 航点 RouteLane、双向 PathElement、船舶目标 | 先修复停靠点/网络绑定，不能反复重建同一线路 |
| 已派船但不来港口 | 当前目标是否仍为外部连接、有效路径、移动状态 | 观察下一段运行，区分正常候发与缺失路径 |
| 客运正常但货运异常 | 两套独立停靠点、货运路径及主路连接 | 分别验收客货；修复一条后复查另一条 |
