# 规划算法与边界

本文说明候选生成、筛选、排序、搜索回退和数据复用的实现边界。算法输出用于选择下一步预览对象，不代替原生施工校验。

## 1. 阅读入口与共同约束

| 内容 | 入口 |
| --- | --- |
| 建筑选址与升级预留 | 第2节；[建筑指南](../guides/buildings/BUILDING-GUIDE.md) |
| 服务、教育和交通批量分析 | 第3节 |
| 街区搜索与几何筛选 | 第4节 |
| 管线和道路寻路 | 第5节 |
| 缓存、并发与恢复 | 第6节；[目录缓存](prefab-catalog-cache.md) |
| 性能指标和基准 | 第7节 |
| 减少重复规划数据 | [规划引用与紧凑响应](planning-token-efficiency.md) |

所有算法保留原生预览、费用上限、永久实体回读和真实连接验收。粗筛通过或评分较高不表示可以直接施工；数据缺失不能当作无障碍、平地或容量充足。算法优化不自动改变建筑输入顺序或施工依赖。

## 2. 建筑选址

### 2.1 候选处理顺序

1. 沿道路多点采样，并按空间分区保留候选，避免候选集中在局部区域。
2. 使用考虑旋转的矩形包围盒筛除碰撞和预留占地冲突。
3. 按建筑类别进行贪婪评分，按排名尝试原生预览。
4. 批量建筑仍按输入顺序施工，后续选址重新查询施工后的实时数据。

贪婪评分用于候选排序，不保证整组建筑布局的全局最优。参数及预留用法见[建筑指南](../guides/buildings/BUILDING-GUIDE.md)。

### 2.2 升级预留与候选补充

- `size_m` 保留建筑本体尺寸。
- `reserved_size_m` 保存包含升级预留的尺寸，随规划持久化；后续绑定和规划碰撞校验统一读取。
- 预留占地过滤后，可用候选不足预算时逐步增加候选数，最多32个；不因此扩大原搜索范围。

## 3. 服务、教育与交通分析

### 3.1 批量查询

服务覆盖批量分析读取一次城市快照，并建立本次请求专用的空间索引；请求结束后销毁，施工后重新查询。

教育和交通分析支持 `positions`，一次传入1–32个坐标，与单点或实体中心选择器互斥。返回 `items` 按输入顺序排列，并提供 `snapshot_reads=1`。

| 分析类型 | 实现方式 |
| --- | --- |
| 教育 | 按学生当前所在建筑和教育等级聚合人数，再建立空间索引 |
| 交通 | 先确定候选范围内站点，再统一遍历线路汇总候车人数，避免逐站重复扫描全部线路 |

旧模组不支持批量查询时，回退逐点分析，并按城市会话记录能力，避免每栋都重试不支持的接口。

### 3.2 统计口径

| 字段或指标 | 含义 |
| --- | --- |
| `nearby_waiting_passengers` | 范围内全部匹配站点的候车人数，不受 `stop_limit` 限制 |
| `listed_waiting_passengers` | 实际返回站点明细的候车人数 |
| 教育容量总计 | 范围内所有学校的容量；分类评分再按目标学校的教育等级过滤 |

旧版交通总数只累计返回明细。依赖旧语义的调用方应改读 `listed_waiting_passengers`，不能把截断明细的总和当作范围总量。

## 4. 街区选址与空间筛选

### 4.1 几何和地形处理

- 对建筑、水域、地形和道路采样点建立空间索引。
- 道路按实际Bezier曲线采样，不能把控制点当作道路上的点。
- 建筑包围盒考虑旋转，跨格大占地查询需要去重。
- 每个候选的地形统计合并为一次遍历，保留边界包含、未知数据和负高程的处理。
- 地形缺失或无效时返回 `terrain_known=false`、空坡度/高差，并增加未知数据惩罚，不当作平地。

### 4.2 粗到细搜索

细网格超过4096个候选位置时：

1. 用四倍步长初筛。
2. 将搜索范围分成4×4个区域，各保留一个最优种子。
3. 在种子周围细化。
4. 细化后仍没有无冲突候选时，回退细网格搜索。

这是近似搜索，不保证全局最优。返回以下字段用于检查搜索过程：

| 字段 | 用途 |
| --- | --- |
| `search_strategy` | 当前搜索策略 |
| `evaluated_candidates` | 实际评估的候选数量 |
| `fallback_fine_search` | 是否触发细网格回退 |

### 4.3 最近道路搜索

先按X坐标排序，以坐标距离下界剪枝；最终仍用欧氏距离比较，等距点沿用原候选顺序，保持评分和连接点选择一致。基准包含排序成本及与穷举结果的校验。

## 5. 管线与道路寻路

### 5.1 管线尝试顺序

`routing=auto` 按以下顺序执行：

1. 去重后尝试直线和两种L形路径。
2. 简单路径全部被原生预览明确拒绝后，读取覆盖最大绕行范围的建筑快照。
3. 快照完整可用时尝试A*；截断或不可用时，不使用不完整障碍数据绕行。
4. 路径简化到最多16个点，再交给原生预览。

`direct` 和 `orthogonal` 不启用A*。预览超时或结果未知时停止，不能改请求ID继续尝试其他路径。

### 5.2 A*参数和复用范围

| 项目 | 当前实现 |
| --- | --- |
| 绕行边界 | 依次尝试128、256、512米 |
| 默认网格 | 16米；长距离按格点上限自动加粗 |
| 细化回退 | 失败后在上限内尝试半步长细化 |
| 搜索上限 | 最多6次，每次最多16000个格点 |
| 代价和状态 | 代价包含长度和转弯，状态保留方向 |
| 障碍检测 | 每段与障碍包围盒做整段相交检测 |
| 障碍索引 | 同一次调用内复用包围盒和空间索引 |
| 边通行缓存 | 本次搜索内复用；不同网格独立，不能混用格点编号 |

空间索引按查询范围选择遍历格子或已有桶，并支持首个命中即返回。

### 5.3 适用边界

管线绕障只使用平面建筑几何代理，不模拟地形、地下深度或真实网络容量。部分地下管线本来可以穿越地面建筑，因此仅用于简单路径失败后的补充，不是通用地下可施工性证明。

道路原有A*算法保持不变，仅把建筑障碍查询改为空间索引，减少逐格线性扫描成本。

## 6. 缓存、并发与失败恢复

### 6.1 区分复用对象

| 对象 | 有效范围 | 后续仍需检查 |
| --- | --- | --- |
| 服务、教育、交通空间索引 | 单次分析请求 | 下次分析、施工后的实时数据 |
| 管线障碍索引与边通行结果 | 单次调用或单次搜索，见第5节 | 新请求的障碍数据与原生预览 |
| Prefab目录 | 当前MCP进程、城市会话内的有期限缓存 | 会话状态、可用性和现场施工验证 |
| 规划引用与施工日志 | 持久化存储，受会话及审批约束 | 原生事务、永久对象回读 |

目录缓存由统一服务管理，同一会话、工具和查询参数的进行中请求共享Promise；错误不作为资产不存在保存，失效后迟到结果不能回写。目录缓存不包含地图道路或建筑实例，详细TTL、刷新和统计见[目录缓存指南](prefab-catalog-cache.md)。

### 6.2 规划请求和施工锁

- 同一 `request_id`、相同参数的并发建筑规划共享一个Promise；参数不同返回 `IDEMPOTENCY_CONFLICT`。
- 取得施工锁后，再检查已完成和不确定事务记录，避免排队期间记录变化导致重复预览。
- 内部批量规划不等待占用同一施工锁的外部请求，避免互相等待。
- 单Agent的高层工具仍可能并行查询；查询合并不表示允许并行提交城市写事务。

### 6.3 必须停止的情况

建筑预览超时、城市会话改变或结果未知时，立即停止候选回退。即使 `continue_on_error=true`，批量施工与计划绑定也必须停止。

错误保留 `recovery_required`、原 `operation_id`（若已取得）及预览 `request_id`。同一建筑规划请求在当前MCP进程内保留错误，重复调用不会另开预览。先检查原事务并处理恢复，再决定是否用新规划请求继续；不能通过更换ID绕过不确定结果。

持久化施工句柄的恢复约束见[规划引用与紧凑响应](planning-token-efficiency.md)，不要把施工日志当作可随意删除的缓存。

## 7. 性能测量与验证

### 7.1 `performance` 字段

| 字段 | 统计内容 |
| --- | --- |
| `elapsed_ms` | 整个请求的墙钟耗时 |
| `stages_ms` | 发现、排队、候选生成与过滤、分析、评分、预览等阶段耗时 |
| `queries` | 工作流统计包装器观测到的工具调用次数、失败次数和累计耗时 |
| `counters` | 候选数量、预览次数等计数 |

解释时注意：

- 未命中缓存的查询耗时包含通信与游戏执行，不能解释为纯游戏算法耗时。
- 当前目录缓存位于部分统计包装器之下；缓存命中或等待共享Promise也可能计入工作流 `queries`，不能直接当作实际桥接往返数。缓存统计另读 `inspect_prefab_catalog_cache`。
- 并行查询累计耗时可能超过请求墙钟耗时；共享查询的等待者也会承担等待时间。
- 阶段和查询统计是不同视角，不能相加。
- 错误响应保留已收集的统计；幂等命中沿用原计划统计，不代表重新执行了一次测量。

### 7.2 离线基准

在 `mcp/` 目录运行：

```powershell
npm run bench:planning -- 7
```

或在项目根目录保存报告：

```powershell
node mcp/benchmark-planning.mjs 7 > artifacts/planning-benchmark.json
```

- 使用固定随机种子，重复次数为1–100；每项预热两次。
- 覆盖三个规模的索引/线性扫描对照、街区搜索、管线绕障，以及批量/逐点分析的模拟工作流。
- 输出中位数、P95、场景规模和正确性校验结果。
- 不连接游戏，不修改城市。

查询次数和场景结果可复现，耗时受机器与负载影响。小数据量下建索引不一定更快，不依据单次测量增加优化阈值。

### 7.3 验证范围与结论限制

现有验证覆盖负坐标空间索引、跨格大占地去重、旋转碰撞、真实曲线采样、批量查询刷新、预留占地传递、复杂绕障和搜索上限。目录缓存及持久化引用的专项验证见对应指南。

查询次数、搜索量和JSON字节数都不等于实际模型token用量，也不等于游戏端到端耗时。真实城市中的运行性能、施工结果和运营成效仍需实测。

规划记录解析、施工图渲染、空间索引复用和统计口径见 [规划计算缓存](planning-computation-cache.md)。
